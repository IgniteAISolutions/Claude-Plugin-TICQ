# The acceptance bar

Binary. Every box ticks or the build is not live. A build where four seats pass and one
does not is not live for that seat, and the team outcome is judged on the whole.

Carried from the run-sheet and field manual this plugin was built from, which split it per seat and
team-wide. The split matters, because a team-wide pass hides a seat that is stuck.

## Per seat

- [ ] **Context files complete.** `CLAUDE.md` and `About Me/` written from this person's
      own answers, with no placeholder left in either. Square brackets count as missing.
- [ ] **A real voice profile**, and a draft through it that sounds like them. Tested in
      the room, on something they actually wrote.
- [ ] **Three or more skills fired on their own real work**, each with a logged output.
      A demo on invented data does not count.
- [ ] **One scheduled task created, classified, and fired**, with output the person has
      seen.
- [ ] **Connectors returning data**, tested one live read each, rather than showing as
      enabled.
- [ ] **Memory carries.** A fact written, a fresh session started, the fact recalled.
- [ ] **A first target with a date**, and a calendar entry holding it.
- [ ] **The run-alone test.** They have run one full session start to finish without
      help, and produced something usable.

The run-alone test is watched rather than reported. You sit there, you do not help, and
if they get stuck the build is not done for that seat. It is the only box that tests the
handover rather than the setup.

## Team-wide

- [ ] **The shared business context loads first**, every session, for everyone.
- [ ] **The task inventory is classified and signed**, with mins per week frozen as the
      baseline.
- [ ] **The function map has an owner and a classification against every task.**
- [ ] **At least one shared scheduled task has fired** on its rhythm and written where
      the team can see it.
- [ ] **The knowledge base holds real client material**, not a placeholder structure.
- [ ] **The firewall is written team-wide**, covering send, money and publish, with the
      role variations named.
- [ ] **A named daily review batch with a target time.** "The review batch runs at 16:00
      and Sam clears it by 17:00" is a service level. "We will check it regularly" is not.
- [ ] **A named champion**, and the next check-in in the diary.

## What happens when a box will not tick

Say so, name the box, and say what it needs and who owns it. Then record the rest as
passing.

Never call it live early. The activation date and the 30-day clock start when every box
is true, and both sides agree it in writing.

## The three that get skipped

Worth watching for, because they are the ones that get waved through under time
pressure and they are the ones that matter at day 30.

**The run-alone test**, because it is slow and feels redundant after a day of watching
them work with help. It is the only evidence that the system survives the trainer
leaving.

**The target with a date**, because the room is tired and it feels like admin. It is the
single defect that undid a whole client build.

**Reading the scheduled task's output** rather than confirming it ran. Punctuality
proves nothing about correctness.
